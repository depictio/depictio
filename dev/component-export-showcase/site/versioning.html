Operating an embedded figure

Staying current,
or deliberately not

A figure on someone else's page has a problem a dashboard does not: the dashboard it came from will change, and the page will not know. These are the parameters that decide what happens when it does.

The parameter surface

Everything the export URL accepts. All are optional; the defaults render the component exactly as the dashboard has it persisted.

ParameterValuesWhat it decides
format json · html A Plotly spec you render yourself, or a self-contained page you frame. Prefer json.
theme light · dark Which palette the server bakes in. Usually irrelevant for json, since you restyle anyway.
filters JSON array Narrows the data before the figure is built. Same predicates the live dashboard applies.
controls JSON object Intra-viz state: which case a multi-view renderer shows, a normalisation mode, a top-N.
expect_version integer Pin. Answers 409 instead of silently serving a figure built from a newer dashboard.

POST to the same path takes filters, controls and theme in the body, for payloads too large to URL-encode.

Three postures

Pick one deliberately. The failure mode of not choosing is a page that looks current and is not.

Track the dashboard

Fetch on load. No version pin.

The figure always shows what the dashboard shows. Correct for a surveillance page, a status board, anything whose job is to be current.

Risk: a dashboard edit changes your page with no review.

Pin to a version

?expect_version=7

Fetch live, but fail loudly if the dashboard has moved past the version you were built against. The 409 names both versions, so a CI check can surface drift as a diff rather than a surprise.

Correct for a report that cites specific numbers.

Freeze the bytes

Save the JSON. Commit it.

The response carries its provenance in meta, so a committed .json still says which dashboard version and which contract produced it, months later with no headers left.

Correct for a published figure. It must never move.

Checking cheaply

Every response carries a weak ETag over everything that varies the body — dashboard version, save time, component, format, theme, filters and controls. Re-fetching a 300 KB figure to learn nothing changed is the thing to avoid.

The exchange

GET …?format=json
→ 200  ETag: W/"3dfd84…"        full body

GET …?format=json
If-None-Match: W/"3dfd84…"
→ 304                           no body, ~200 bytes

The tag is weak on purpose. meta.generated_at is fresh on every call, so two builds are semantically identical but never byte-identical; a strong validator would be a lie.

Filtering, two ways

A filter is a Depictio component like any other, so you can either embed the real control or build your own from the values it advertises. Both drive the same ?filters= parameter.

Your own control

Discovering the contract

GET /export/dashboards/{id}/components
      ?include_filter_options=true

→ { "component_type": "interactive",
    "dc_id": "646b0f…ca5",
    "filter": {
      "interactive_component_type": "MultiSelect",
      "column_name": "habitat",
      "options": { "kind": "categorical",
                   "values": ["Groundwater", "Riverwater",
                              "Sediment", "Soil"] } } }

Applying it

GET …/components/{figure_id}?format=json
      &filters=[{"interactive_component_type":"MultiSelect",
                 "column_name":"habitat",
                 "value":["Soil"]}]

→ meta.filter_applied: true

dc_id is what tells you which filters govern which figures: a control only applies to components over the same data collection.

Multi-view components

Some renderers present several views of one component — in the dashboard that is a tab bar. Over the API it is ?controls=, and without it an export can only ever produce the persisted default.
